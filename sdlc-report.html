Major — FixedGET /api/items?tag= built a LIKE pattern from unescaped user input; a tag containing % or _ would act as a SQL wildcard, breaking the exact-match guarantee (AC-07/ADR-003). Fixed by escaping % and _ with an ESCAPE clause.

System Architecture

High-Level Design

Extends the existing items domain rather than introducing a new resource: a nullable tags TEXT column added via an additive SQLite migration; zod-validated and server-normalized (trim/lowercase/dedupe) tags on POST/PATCH /api/items; an exact-match tag filter on GET /api/items via a comma-wrapped, wildcard-escaped LIKE clause folded into the existing whereClauses/args pattern; and frontend additions (Item.tags type, API client fields, a new TagFilter.tsx mirroring StatusFilter.tsx, tag pills in ItemCard, and full wiring in Dashboard.tsx). No new services, tables, or external dependencies were introduced.

Architecture Decision Records

ADR-001Single comma-separated TEXT column on items instead of a normalized tags/item_tags join table, per the requirements' no-new-tables constraint.
ADR-002Tag count/length validation runs before case-insensitive deduplication, so a submission of 11 raw tags is rejected even if it would dedupe to ≤10 — a conservative, security-favoring interpretation of AC-04.
ADR-003Exact-match tag filtering via a comma-wrapped LIKE pattern (',' || tags || ',' LIKE '%,tag,%') instead of a raw substring LIKE, to satisfy AC-07 without a join table or FTS.
ADR-004TagFilter options are derived client-side from the currently-loaded page of items rather than adding a new "list distinct tags" endpoint, per the requirements' explicit scope constraint.
